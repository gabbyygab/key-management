TASK B5.3 - THE CONFLICT DETECTION ALGORITHM (core deliverable)
  File: scheduling/services.py

  def find_conflicts(room, day_of_week, start_time, end_time, term,
                     exclude_block_id=None) -> list[ScheduleBlock]

  Overlap rule - two blocks conflict when:
        existing.start_time < new.end_time
    AND existing.end_time   > new.start_time
  (Touching endpoints do NOT conflict: a 09:00-10:00 and a 10:00-11:00 block
  are both valid. This is the classic off-by-one; get it right.)

  Requirements:
  - Must filter by the same room, same day_of_week, same term, is_active=True
  - Must honor exclude_block_id so editing a block does not conflict with
    itself
  - Must be a single DB query, not a Python loop over all blocks
  - Raise ScheduleConflictError listing every conflicting block

  def validate_block(block) -> None
    - end_time > start_time
    - block falls inside the term date range
    - no conflicts via find_conflicts()
    - room.is_active and room.status != MAINTENANCE/INACTIVE

*** SECURITY ***

TASK B8.1 - [SECURITY/HIGH] Open redirect in the login view
  File: accounts/views.py:30
  Current:  return redirect(request.GET.get("next") or "dashboard")
  Problem:  The "next" parameter is taken straight from the query string and
            passed to redirect() with NO validation. An attacker can send
            /accounts/login/?next=https://evil.example.com - after a real
            successful login the user is redirected off-site. This is a
            textbook open-redirect / phishing vector.
  Fix:      Validate the target before redirecting, using Django's helper:
              from django.utils.http import url_has_allowed_host_and_scheme
              nxt = request.POST.get("next") or request.GET.get("next")
              if nxt and url_has_allowed_host_and_scheme(
                      nxt, allowed_hosts={request.get_host()},
                      require_https=request.is_secure()):
                  return redirect(nxt)
              return redirect("dashboard")
  Also:     The login template (templates/accounts/login.html:31) does NOT
            forward "next" in a hidden input, so the redirect target is lost
            on POST anyway. Add <input type="hidden" name="next"> and read it
            from request.POST too, or drop the feature entirely. Right now it
            is both broken AND unsafe.
  Test:     Assert that ?next=https://evil.example.com redirects to the
            dashboard, and that ?next=/keys/ still works.

TASK B8.2 - [SECURITY/MEDIUM] Logout accepts GET - CSRF-able
  File: accounts/views.py:35-41
  Current:  The view logs the user out on GET as well as POST, with a comment
            calling it "guard convenience".
  Problem:  A state-changing action on GET has no CSRF protection. Any
            <img src="/accounts/logout/"> on any page logs the guard out.
            Worse here than usual: logout FIRES THE user_logged_out SIGNAL,
            which CLOSES THE GUARD SHIFT (transactions/signals.py). A drive-by
            GET can therefore end a guard shift and block them from releasing
            keys until they log in again.
  Fix:      Make logout POST-only. Add @require_POST and delete the GET
            fallback. templates/partials/logout_modal.html already submits a
            proper POST form with {% csrf_token %}, so nothing in the UI
            breaks. Remove any remaining GET logout links.
  Test:     GET /accounts/logout/ returns 405 and the session stays alive.

TASK B8.3 - [SECURITY/LOW] State-changing toggle not POST-guarded
  File: accounts/views.py:84-92  (borrower_toggle)
  Problem:  The body is wrapped in "if request.method == POST" so a GET is
            harmless, but the view is not decorated @require_POST. It silently
            redirects on GET instead of rejecting, which hides mistakes and
            invites the same pattern to be copied into new toggle views
            (user_toggle, room_toggle, schedule_toggle in Sections 2/3/5).
  Fix:      Add @require_POST and drop the inner method check. Apply the same
            decorator to EVERY new toggle/approve/reject view you write.
            transactions/views.py:100 and :118 already do this correctly -
            follow that pattern.
