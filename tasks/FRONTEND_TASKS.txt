  File: static/js/modal-form.js (new)
  The pattern for every add/edit modal:
  - Fetch the form HTML from the backend endpoint into the modal body
    (GET ?modal=1 returns just the form partial)
  - Submit via fetch() POST with X-CSRFToken header
    (read csrftoken from the cookie - Django requires this)
  - On 200/201: close modal, refresh the affected list region (or full reload
    for v1), show a success toast
  - On 422: re-render the form inside the modal WITH Django field errors
    inline under each field - do NOT close the modal and do NOT lose the
    user's typed input
  - On 403: show "You do not have permission" and close
  - Disable the submit button + show a spinner while in flight (prevents
    double-submit, which matters a lot on the borrow action)

TASK F7.1 - [SECURITY] Login form drops the "next" parameter
  File: templates/accounts/login.html:31
  Current:  <form method="post" class="mt-5 space-y-3">{% csrf_token %}
  Problem:  The form has no action and no hidden "next" field. The view
            (accounts/views.py:30) reads "next" from request.GET, but on POST
            the query string is gone - so redirect-after-login silently never
            works. Backend TASK B8.1 is also fixing an open-redirect hole in
            that same line.
  Fix:      Add inside the form:
              <input type="hidden" name="next" value="{{ next|default:'' }}">
            Coordinate with backend B8.1 - they will validate the value with
            url_has_allowed_host_and_scheme and pass "next" into the template
            context. Do NOT build your own redirect logic in JS.

TASK F7.2 - Sidebar mislabels admins as guards
  File: templates/partials/sidebar.html (user chip, near the bottom)
  Current:  {{ user.role|default:"GUARD" }}
  Problem:  The |default:"GUARD" filter means any user whose role is empty or
            falsy displays as "GUARD". On an admin account that is actively
            misleading in a system whose whole point is role separation.
  Fix:      Use {{ user.get_role_display }} with no default. Django generates
            that method from the Role.choices on the model, so it prints
            "Admin" / "Guard" / "Faculty / Staff" properly.
  Same file: the avatar initials fall back to "GU" - replace with initials
            derived from the actual name, or a neutral placeholder.

TASK F7.3 - Broken active-state logic in the sidebar
  File: templates/partials/sidebar.html (Key Inventory and Key Categories
        links)
  Current:  {% if ns == 'keys' and current == 'key_list' or current == 'key_create' or current == 'key_update' %}
  Problem:  Django template {% if %} binds "and" tighter than "or", so this
            parses as:
              (ns == 'keys' AND current == 'key_list') OR current == 'key_create'
              OR current == 'key_update'
            The namespace check only applies to the first branch. Any future
            view named key_create/key_update in a DIFFERENT namespace would
            wrongly highlight this link. The Key Categories link has the same
            bug.
  Fix:      Group the url names explicitly, e.g.
